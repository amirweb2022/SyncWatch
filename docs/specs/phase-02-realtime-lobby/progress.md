## Unresolved architectural limitations

- Realtime channels have no durable room registry. A joining client can reject an empty Presence snapshot, but cannot distinguish a never-created code from a lobby whose last member just left; there is no durable `lobby-not-found` fact.
- Public channels plus no Auth provide no per-lobby authorization. A short code is discoverability, not a secret or trusted access check.
- Presence capacity checks are not atomic. Concurrent joins can exceed the configured cap, and clients cannot safely choose an excess member to evict.
- Simultaneous creators can both observe an empty code channel and become members of the same lobby.
- Host is derived from each client's currently synchronized Presence set and untrusted client timestamps. The deterministic tie-break agrees for identical snapshots; differing snapshots or clock skew can cause temporary host disagreement.
- Presence expiry after crashes/network partitions is service-managed and eventually consistent. The client can label its last snapshot stale but cannot guarantee immediate stale-member removal.
- Public Realtime must be enabled in Supabase project configuration. If disabled, the client can report a connection/permission failure but cannot change project settings.
